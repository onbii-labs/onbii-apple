# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Onbii Apple is **the** real macOS/iOS/watchOS implementation of Onbii, a
knowledge-object system — not a prototype or throwaway. It contains the apps
that produce and inspect `.onbii` objects and the shared Swift packages behind
them. **Milestone 1 is the current phase** of that implementation, so today's
format and format-level choices are deliberately provisional (the manifest is
versioned `0.1.0-draft`) and expected to evolve — but the code, structure, and
boundaries here are the production foundation, built to last, not to be thrown
away. The shared product/format specification lives in a submodule at
`docs/spec` and is the source of truth for product/format decisions; this repo
holds the Apple-specific implementation.

## Read the vision first

**Before non-trivial work, read `docs/spec/docs/VISION.md` and
`docs/spec/docs/PRINCIPLES.md`** (in the spec submodule — run
`git submodule update --init --recursive` if `docs/spec` is empty). They carry
the project's overview and spirit, and they are not decoration: they decide what
this code is allowed to do.

The one-line vision: *frictionless access to knowledge that keeps becoming more
connected and more useful, and still belongs to the person who created it.* Onbii
is a **memory-aware knowledge system**, closer to a memory-aware CRM than a
note-taking or meeting-notes app — the goal is connections that let knowledge
build on itself, not prettier summaries.

The principles that most directly constrain code here:

- **Local-first & user-owned storage.** A single device and a local folder must
  be enough. The answer to "where is my knowledge?" is an ordinary, inspectable
  file/folder — never a vendor backend. Cloud (iCloud) is optional sync, not the
  only home.
- **Preserve sources.** The original recording/file is the irreplaceable truth;
  derived artifacts (transcripts, summaries, mixdowns) can always be regenerated.
  A lost source cannot.
- **Derived data is not truth.** Machine interpretations stay distinguishable
  from sources and human edits, and carry provenance (what/from-what/when).
- **Human edits are first-class.** Corrections and annotations are preserved and
  marked; reprocessing must never silently overwrite them — it adds or supersedes.
- **Applications are views.** Our apps (and Finder, Quick Look, CLI, Obsidian…)
  are surfaces over user-owned objects. Knowledge must outlive any app that
  touches it; no view is required to keep an object usable.
- **Stable identity over filenames.** Objects carry opaque stable IDs; links must
  survive renames and moves.
- **Bring your own components / clear boundaries.** Recorder, storage, AI, and
  client are all replaceable. Keep source-adapter / capture-adapter / processing /
  storage / view responsibilities separate even when convenient to merge them.

If a change would make Onbii own the user's knowledge, hide the source, treat
derived output as truth, or make an app the place knowledge truly lives, it is
almost certainly wrong regardless of how convenient it is.

**Decision records.** `docs/spec/docs/decisions/` holds ADR-style records
(`0001`–`0028`, each with context / decision / consequences) preserving the
reasoning behind choices future contributors are likely to question. Consult
them before revisiting a settled question or working near an unsettled one:

- Records marked **Open** are the ones actively in flux and explain why parts of
  this repo are deliberately provisional — e.g. `0025` (exact `.onbii` package
  format open), `0026` (identifier scheme open), `0024` (first producer workflow
  open). Don't harden an Open decision into an assumption.
- Load-bearing **Accepted** records worth knowing: `0005` (Onbii is *not* an AI
  meeting-notes product), `0006` (capture certainty before intelligence — get the
  source safely archived before building intelligence on top), `0003` (bundles
  over loose sidecar files), `0022` (no user-facing graph database),
  `0023` (no hidden retrospective recording — recording is always explicit).

## Working with the project structure

- **Open `OnbiiApple.xcworkspace`** — the single entry point. It references the
  two generated app projects and the `Packages/` Swift package.
- **Never open or hand-edit the `.xcodeproj` files under `Apps/`.** They are
  generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from each app's
  `project.yml`. To change build settings, targets, deps, entitlements, or
  Info.plist wiring, edit `project.yml` and regenerate.
- The Swift package lives **outside** the app projects on purpose (avoids an
  ambiguous nested project/package workspace). Apps consume it as a local package.
- The spec is a git submodule. After cloning:
  `git submodule update --init --recursive`.

## Common commands

```sh
# Run all package tests (uses swift-testing, not XCTest)
swift test --package-path Packages

# Run a single test by name (function or suite name)
swift test --package-path Packages --filter resourcePathCannotEscapeBundle

# Regenerate an app's Xcode project after editing its project.yml
cd Apps/OnbiiMac && xcodegen generate      # or Apps/OnbiiIOS

# Build an app (schemes live in the generated projects)
xcodebuild -workspace OnbiiApple.xcworkspace -scheme OnbiiMacApp build
xcodebuild -workspace OnbiiApple.xcworkspace -scheme OnbiiIOSApp -destination 'generic/platform=iOS Simulator' build
```

Tests are written with **swift-testing** (`import Testing`, `@Test`, `#expect`),
not XCTest. All package logic is validated at the package level; the apps are
thin UI shells.

## Package architecture

Five libraries in `Packages/` (swift-tools 6.0, Swift 6 language mode; macOS 14 /
iOS 17 / watchOS 10):

- **`OnbiiCore`** — the logical model only: `OnbiiManifest`, `OnbiiResource`,
  `OnbiiProvenanceEvent`, `OnbiiObjectID`, and manifest validation. No
  dependencies. Object IDs are **opaque** (currently UUIDs) — never infer
  semantics from the value.
- **`OnbiiArchive`** (depends on `OnbiiCore`) — reads/writes the physical
  `.onbii` bundle. Contains the writer, reader, enricher, import-request model,
  recording-name generation, and iCloud archive resolution.
- **`OnbiiCapture`** (no deps) — the **acquisition boundary**: microphone
  recorder, Core Audio system-audio tap/probe, the dual-source capture session,
  and Watch recording metadata. Much of it is `#if os(macOS)`-gated.
- **`OnbiiTranscription`** (no deps) — the **replaceable processing boundary**:
  Apple on-device `Speech` transcription. Gated `#if os(macOS) || os(iOS)`.
- **`OnbiiUI`** (depends on `OnbiiCore`, `OnbiiArchive`) — the shared **presentation
  layer** for Mac and iPhone: the adaptive brand palette, the Prata display face,
  the object-status badge, the brand mark, the shared empty state. Contains no
  knowledge of how objects are written. App icons and each app's global accent
  colour cannot live here (see
  `docs/architecture/visual-identity.md`); the Watch deliberately does not depend
  on it.

These boundaries are deliberate: capture adapters *acquire* media, source
adapters *normalize* it, the archive *preserves* it, transcription *derives*
from it. None of them owns another's job — e.g. `OnbiiCapture` never writes
bundles and `OnbiiTranscription` never mutates sources.

## The `.onbii` bundle and the central data flow

An `.onbii` object is a **directory** (package on macOS) containing
`manifest.json`, a human-readable `content.md`, and a `source/` folder with the
original files. See `docs/architecture/milestone-1-bundle-profile.md` for the
authoritative description.

Every acquisition path converges on one pipeline:

```
mic capture / Files import / Watch transfer / dual-source call capture
        -> OnbiiImportRequest  (normalized input)
        -> OnbiiBundleWriter    (preserve + manifest + provenance)
        -> user-selected archive (iCloud Drive container, local fallback)
```

Invariants that the writer/reader enforce and that new code must uphold:

- **Originals are preserved, never modified or mixed.** Import *copies* the
  source. Dual-source call capture stores the system-audio and microphone legs
  as two separate `source` resources; any mixdown is *derived* data with its own
  provenance, not a replacement.
- **Atomic, non-destructive writes.** `OnbiiBundleWriter` stages the whole
  bundle in a hidden temp dir beside the destination, validates the manifest,
  then moves it into place. It **refuses to overwrite** an existing bundle.
- **Staged capture files are deleted only after** the bundle preserves them; on
  failure the staging path is retained and surfaced to the user.
- **Readers validate before presenting.** `OnbiiBundleReader` confirms the
  manifest and that every declared resource exists; malformed/incomplete bundles
  are errors, never partially trusted.
- **Provenance is recorded for every action** (`imported`, `captured`,
  `rendered`, later `transcribed`). Provenance may only reference resources
  declared in the same manifest; resource paths must be safe bundle-relative
  paths (validated in `OnbiiCore`).

## Apps

Generated from `project.yml`; sources under `Apps/<App>/Sources`.

- **OnbiiMac** — macOS producer + inspector. Uses Archive, Capture,
  Transcription. App Sandbox; access only to user-selected locations (persisted
  via security-scoped bookmarks). Hardened runtime enabled.
- **OnbiiIOS** — iPhone producer + Watch receiver. Uses Archive, Capture, and
  **embeds the Watch app as a target**. Receives original Watch recordings over
  Watch Connectivity; only the iPhone creates the `.onbii` object (the Watch
  never defines a second format). Does not transcribe in Milestone 1.
- **OnbiiWatch** — watchOS capture companion. Its sources live at
  `Apps/OnbiiWatch/Sources`, but its **target is defined inside
  `Apps/OnbiiIOS/project.yml`**, not a standalone project. Uses Capture.

Bundle IDs: `com.yepyr.onbii` (Mac and iOS), `com.yepyr.onbii.watchkitapp`
(Watch). The default archive is the iCloud Drive container
`iCloud.com.yepyr.onbii` → `Documents/Onbii Archive`, with a local-container
fallback.
